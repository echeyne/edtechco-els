## The job

Build a rule-based (regex/heuristic) structure extractor and grade it with the
**same** `eval_detector` suite against the **same** goldens, so the numbers sit
directly beside the LLM detector's. This closes the paper's "no external
baseline" gap — right now the LLM lift is unquantified, and it is the sort of
thing a reviewer reliably asks about.

**Needs ZERO Bedrock.** The baseline is pure Python; grading compares against
goldens on disk. Do not let it consume Opus quota — that is reserved for the
Task 3 run-3 completion and Task 6.

## ⚠️ The one rule that must not be broken

`CLAUDE.md`'s central design direction is that `detector.py` and `parser.py` are
**LLM-driven, not rule-driven**, and that per-state regexes in those files are
"a regression in disguise." This baseline is a **deliberate throwaway that lives
only in `evaluation/baselines/`**. It is emphatically NOT a licence to move any
of its logic into `src/els_pipeline/`. If you find yourself editing
`detector.py`, stop — that is out of scope for Task 4.

## How to build it

1. Put it under `evaluation/baselines/` (new package). Suggested:
   `evaluation/baselines/rule_based.py` exposing a function that takes the same
   `list[TextBlock]` the detector takes and returns `list[DetectedElement]`, so
   the existing grading path can consume it unchanged.
2. Heuristics worth implementing (document-agnostic, per the plan): numbering
   patterns (`1.`, `1.1`, `a.`, `I.A.2`), structural label words
   (`Domain`/`Strand`/`Standard`/`Benchmark`/`Indicator`), ALL-CAPS or
   title-case headings, indentation and font-size cues if the extraction carries
   them, and depth inferred from numbering nesting.
3. Grade with the same matcher. `evaluation/eval_detector.py` already has
   everything: `_match_key`, `_tag_domains`, per-level tp/fp/fn, code accuracy,
   the regression cases. Reuse them — **do not** write a parallel grader, or the
   numbers stop being comparable, which is the entire point of the task.
4. Depth map: the baseline has none. Report it as `ABLATED`/`N/A` rather than
   grading it (`eval_detector` already models a third state — see how
   `Config.DEPTH_MAP_ENABLED` produces `depth_map_passed = None`).

## Recording the result

Follow the established pattern exactly — see `paper/results/task3_20260822/`
for the shape:

- `paper/results/task4_<YYYYMMDD>/` with `findings.md` + `manifest.json`
  (`task`, `date`, `git_commit`, `code_version_hash`, `corpus_tier`, `inputs`,
  `models`, `commands_in_order`, `files`, `caveats`).
- A comparison JSON, and a table generated by adding a builder to
  `paper/analysis/generate_tables.py`. **Do not hand-type a table** (guardrail 6).
  That script now has a `RUN_TAG` constant and refuses superseded tags — add
  `baseline_comparison.tex` alongside the three existing builders.
- **State the corpus tier on every table** (guardrail 1) — these are 8–15pp
  subsets, not full documents.

## Caveats to carry into `findings.md`

- **Never report the detector suite's raw "precision" as quality** (guardrail 8)
  except for KY, whose golden is detection-exhaustive (44 golden vs 44 in-scope,
  zero unmatched). Everywhere else raw precision measures annotation coverage.
  For the baseline this cuts both ways: a baseline that over-emits will look
  worse than it is on precision, and that must be said.
- **The baseline needs its own FP audit before any precision number is
  quotable**, or its precision must be reported as raw-with-caveat. Do not
  silently compare the LLM's *verified* precision against the baseline's *raw*
  precision — that comparison is invalid. This is the single most likely way to
  produce a misleading table here.
- Corpus tier on every table; no full-document claim (that is Task 6).
- If the baseline does unexpectedly well on some state, report it (guardrail 7).
